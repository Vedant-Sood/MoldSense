# MoldSense USB research protocol 1

Firmware 1.0.0-rc1; desktop research 2.0.0-rc1. Transport: USB UART, 115200 baud, 8N1, newline-delimited UTF-8 JSON. One object per LF-terminated line. No network required. Firmware telemetry defaults to one snapshot per second; BSEC retains control of its own measurement/heater schedule. Maximum firmware packet buffer 3072 bytes; console TX buffer 4096 bytes; desktop framing limit 16384 bytes. Oversize lines are rejected and their retained prefix is marked truncated. This is an open local instrumentation protocol, not an authenticated remote-control interface.

## Envelope and time

Every JSON message contains `type`, `protocol_version:1`, `device_id`, `firmware_version`, `boot_id`, `sequence`, and `uptime_ms`. Device ID derives from the ESP32 MAC; boot ID is a random 32-bit session token scoped by physical device ID. Sequence increases across **all packet types**, not just readings. Gaps indicate potentially missing protocol packets; they do not necessarily equal missing sensor observations. Duplicate/out-of-order messages remain in the raw packet archive but do not create duplicate reading rows. A new boot starts a separate sequence domain.

`uptime_ms` is a continuously extended monotonic 64-bit uptime, not UTC. The desktop adds `received_at` (ISO UTC) and `received_epoch` from its clock. Receive time includes serial/OS latency and can jump if the PC clock changes. Keep `boot_id`, sequence and uptime for reconstruction. Firmware `utc_unix_s` remains null without a clock provider. Never infer calendar time from uptime or assume a reboot gap was measured.

All unavailable numeric evidence is JSON `null`, never a fake zero or NaN JSON literal. Unknown extra fields can be archived by older compatible consumers. The desktop rejects incompatible protocol versions and firmware major versions during discovery.

## Reading fields

| Group | Fields / units |
|---|---|
| Air | `temperature_c` compensated °C, `raw_temperature_c`, `humidity_percent`, `raw_humidity_percent`, `pressure_pa`, `dew_point_c` |
| Gas | `gas_resistance_ohms`, `gas_observation_id`, `gas_heater_index`, `iaq`, `static_iaq`, `iaq_accuracy`, `co2_equivalent_ppm`, `breath_voc_equivalent_ppm` |
| BSEC | `stabilization_status`, `run_in_status`, model identity/status; detailed driver/state diagnostics are returned by `STATUS` / `SENSOR_INFO` |
| Wall | `wall_cap_raw`, `wall_cap_filtered` (touch or ADC units, not pF), `wall_baseline`, `wall_deviation`, `wall_moisture_index` (relative 0–100), `baseline_id`, `wall_status` |
| Evidence | `environment_risk`, `condensation_risk`, `voc_mold_probability` (0–1 only when valid), `mold_probability` (unvalidated 0–100 index), `confidence`, `risk_level` |
| Explanation | `environment_contribution`, `wall_contribution`, `condensation_contribution`, `voc_contribution` (index points; sum to index) |
| Validity | `air_valid`, `wall_valid`, `baseline_valid`, `data_quality`, `sample_interval_ms`, `air_sample_uptime_ms`, `wall_sample_uptime_ms`, `gas_sample_uptime_ms` |

The exact emitted names are defined by `src/UI/ResearchProtocol.cpp`; the integration fixture in `tests/fixtures/firmware_readings.ndjson` is generated by that actual serializer. Sample uptime fields are underlying 32-bit sample-clock values; use modulo subtraction within the boot to assess age. Streaming a held gas result does not create a fresh gas observation. Desktop gas means/correlation deduplicate `gas_observation_id` within a boot and analyze the selected heater step. AI heater steps must not be pooled against one baseline. IAQ and AI-scan profiles are mutually exclusive on one physical BME688; unavailable virtual sensors stay null.

`data_quality` is evidence quality, not ground truth. Baseline changes have a CRC identifier. `DEVICE_INFO` reports the configured filter, normalization and risk values plus a configuration fingerprint; firmware remains the risk source of truth. Desktop statistics cannot silently alter stored firmware scores.

## Messages

| Type | Purpose |
|---|---|
| `reading` | Sensor and risk snapshot |
| `device_info` | Product, firmware/protocol/BSEC/model/config identity and settings |
| `status` | Sensor/storage/OLED health and state |
| `baseline_info` | Existing dry reference, statistics, confidence, identity |
| `calibration_progress` | Progress, sample count/target, interim mean/median/SD |
| `calibration_complete` | Completion/cancellation result and retained baseline; check `success`, not merely `valid` |
| `model_info` | Name/hash, validation reference, acceptance and model status |
| `warning`, `error` | Fault changes or failed operations; a fault mask is documented in its reason |
| `command_ack` | Correlated request result, reason and optional confirmation token |
| `log_chunk`, `log_complete` | Checked device CSV download |

Fault-mask bits: 1 air unavailable, 2 wall invalid, 4 no baseline, 8 storage fault, 16 OLED failure, 32 VOC model/evidence unavailable. Missing untrained VOC is expected in the supplied configuration. Boot diagnostic and human diagnostic lines are not JSON: retain them as diagnostic raw frames, not malformed readings to be converted to zero.

## Commands

Commands are ASCII lines, at most 95 characters. Preferred syntax is `@<decimal request_id> COMMAND [argument]`. Request IDs are unsigned 32-bit. Example:

```text
@42 PING
@43 STATUS
@44 START_BASELINE
@45 CONFIRM 1A2B3C4D
```

The last token is illustrative; use the actual `confirmation_token` from request 44. An ACK has `request_id`, `command`, `success`, `reason`, and (only if required) a token as eight hexadecimal digits. The desktop expires unanswered requests after five seconds and never retries a consequential command blindly.

| Command | Behavior |
|---|---|
| `PING`, `DEVICE_INFO` | Identification/configuration packet and ACK |
| `STATUS` | Health packet and ACK |
| `GET_BASELINE` | Reference/statistics and ACK |
| `START_BASELINE` | Arms dry-wall calibration; one-use confirmation expires after 15 s |
| `CONFIRM XXXXXXXX` | Executes the armed action after token/state checks |
| `STOP_BASELINE` | Cancels calibration, preserving the prior valid baseline |
| `MODEL_INFO` | Model and BSEC state metadata |
| `SET_SAMPLE_INTERVAL 1000..60000` | Sets telemetry snapshot interval in ms for this boot; not heater scheduling |
| `NEW_SITE` | Arms reset of observed exposure history after moving probe |
| `DUMP_LOG` | Requests CRC-checked NDJSON log download |
| `STOP_DUMP` | Cancels a pending/active download |
| `CLEAR_LOG` | Arms deletion of `/ms_log.csv` only; never BSEC/wall state or desktop archive |
| `HELP` | Lists commands |

Human-only diagnostics: `EXPLAIN`, `BASELINE`, `SENSOR_INFO`, `CALIBRATE`, `CANCEL`, `DUMP`. Human `FORMAT_LOGS` is guarded and refused while the filesystem is mounted. It formats the entire log partition if deliberately confirmed; back up all existing files first. No BSEC reset/training command is exposed.

## Download integrity

Each log chunk carries byte `offset`, hex data (up to 64 bytes), and IEEE CRC32 of decoded bytes. Completion includes transferred `bytes` and independently captured `expected_bytes` from the opened file size. A short read emits `error`, never successful completion. Log appends are paused during download; sensor telemetry may continue. Desktop validates CRC, contiguous offsets and final length, writes `.csv.partial`, then renames only after validation and stores a SHA-256 sidecar. Interruptions retain a partial file; restart the download from offset zero rather than concatenating sessions. CRC detects transmission corruption, not malicious tampering.

## Discovery and recovery

Desktop enumerates likely USB serial ports and requires an actual MoldSense `PING` reply; a port name alone is not identity. Multiple responding devices require selection. Reconnect may search another port but must match the expected physical device ID. Disconnect events, sequence gaps and reboots remain recorded; chart lines break at communication gaps. USB drivers may reset an ESP32 when a port opens even though the application avoids asserting DTR/RTS. Verify this on the real adapter before research collection.
